O enunciado pede um processo ETL (Extract, Transform, Load) completo, com dados de várias origens e formatos, transformações de limpeza e de negócio e vários destinos. O tema vem de um projeto pessoal, o hacampo ("Há campo?"): um quadro público que mostra, a qualquer jogador, que campos de ténis estão livres ou ocupados num clube, sem ter de telefonar.

2. Problema

Em muitos clubes de ténis não se consegue ver online se há campos livres. As marcações estão espalhadas por sistemas que não falam entre si: num clube são escritas num caderno no bar e passadas para Excel; noutro há uma aplicação só para sócios; num complexo municipal estão na agenda da câmara. Quem quer jogar tem de ligar para cada um.

O objetivo do trabalho é integrar as marcações de três clubes num único quadro de disponibilidade. Para isso é preciso resolver problemas típicos de integração ao nível dos dados:

ProblemaExemplo nos dados
Formatos diferentesCSV com ;, JSON com objetos aninhados, XML com atributos e validação por XSD
O mesmo valor escrito de várias formasdatas 21/10/2026, 2026-10-21, 21-10-26; horas 18h, 18:00, 18.30, 18H; campos C1, Campo 1, court 1; telefones +351 912…, 00351912…
Dados incompletos ou inválidosreserva sem hora, data sem ano, campo que não existe, reserva depois do fecho do clube
Registos repetidoslinha escrita duas vezes no caderno; a app envia a mesma reserva duas vezes (mesmo id); reservas canceladas
Dados pessoaisnomes, telefones e emails não podem aparecer num quadro público (RGPD)
Informação de outros sistemasse vai chover num campo descoberto e se já é de noite num campo sem iluminação
Conflitos de negócioduas reservas no mesmo campo à mesma hora

Os clubes e as reservas são fictícios (gerados com erros de propósito, para haver o que limpar). A previsão do tempo é real e vem da API Open-Meteo.

3. Estratégia utilizada

O processo foi dividido em cinco transformações, orquestradas por um job. As três transformações de entrada (T1, T2, T3) tratam cada uma um formato e escrevem todas para a mesma tabela intermédia (staging), já no mesmo formato. A T4 trabalha só sobre essa tabela, por isso não precisa de saber de onde veio cada reserva. Para juntar um quarto clube basta acrescentar uma transformação de entrada.

4. Transformações

4.1 T0 – Previsão do tempo (API REST)

Lê os três clubes da base de dados e monta, em SQL, o URL da API com a latitude e a longitude de cada um e com os parâmetros ${DATA_INICIO} e ${DATA_FIM} (substituição de variáveis ativa). O HTTP client faz um pedido GET por clube. A resposta é JSON com listas paralelas (hourly.time, hourly.precipitation_probability, hourly.is_day), que o JSON input lê a partir do campo da resposta e transforma em linhas: 3 pedidos dão 504 linhas (3 clubes × 7 dias × 24 horas). O resultado substitui a tabela meteo_hora.

4.2 T1 – Clube A: caderno do bar (CSV)

É a origem mais desarrumada. Primeiro, o String operations tira espaços, põe a hora e o tipo em maiúsculas e o nome com iniciais maiúsculas. Depois, o Replace in string aplica as expressões regulares:

CampoExpressão regularSubstituiçãoExemplo
data^(\d{2})/(\d{2})/(\d{4})$$3-$2-$121/10/2026 → 2026-10-21
data^(\d{2})-(\d{2})-(\d{2})$20$3-$2-$121-10-26 → 2026-10-21
hora^(\d{1,2})[H:.]?$$1:0018H → 18:00
hora^(\d{1,2})[H:.](\d{2})$$1:$218h30, 18.30 → 18:30
campo\D(nada)Campo 2, C2, court 2 → 2
telefone\D e depois ^(00351|351)(\d{9})$$2+351 912 345 678 → 912345678

A seguir, quatro passos Regex evaluation validam os valores normalizados. Os grupos de captura extraem logo os números de que o cálculo precisa:

  • data: ^\d{4}-\d{2}-\d{2}$
  • hora: ^(\d{1,2}):(\d{2})$ → h_ini, m_ini
  • duração: ^(?:(\d+)\s*h)?\s*(?:(\d+)\s*(?:min|m)?)?$, que aceita 1h, 1h30, 90min, 60 → dur_h, dur_m
  • telefone português: ^(9[1236]\d{7}|2\d{8})$

O Filter rows envia as linhas incompletas para erros_clube_a.csv. As restantes seguem: a data passa a tipo Data, o Calculator calcula inicio_min = h × 60 + m e fim_min = inicio_min + duração (com NVL para as partes em falta), o Value mapper traduz S/P/A para singulares/pares/aula e o Add a checksum substitui o telefone por um código SHA-256. Esse código permite contar clientes e detetar duplicados sem guardar o número. O último Select values deixa só os campos da staging: o nome e o telefone ficam para trás.

Resultado: 48 linhas lidas, 2 com erro (uma sem hora e uma com a data sem ano), 46 gravadas na staging.

4.3 T2 – Clube B: app de sócios (JSON)

O JSON input usa caminhos JSONPath como $.reservas[*].member.phone para achatar o objeto aninhado do sócio. As reservas com status diferente de confirmed são descartadas. Depois de ordenar por id, o Unique rows deteta os registos que a app enviou duas vezes e redireciona-os, através de um hop de erro, para repetidas_clube_b.csv. As datas ISO (2026-10-21T18:00:00) são convertidas para Data e o Calculator extrai a data sem hora (REMOVE_TIME_FROM_DATE), a hora (HOUR_OF_DAY) e o minuto (MINUTE_OF_HOUR). Nome, email e telefone não passam para a staging.

Resultado: 51 reservas lidas, 7 canceladas, 2 repetidas, 42 gravadas.

4.4 T3 – Clube C: agenda municipal (XML)

Antes desta transformação, o job valida o XML contra clube_c_agenda.xsd. O XSD obriga, por exemplo, a horas no formato HH:MM, a campos T1, T2… e a um tipo de marcação dentro de uma lista fechada; se o XML não cumprir, o processo para antes de ler dados errados. O Get data from XML percorre /agenda/dia/marcacao (uma linha por marcação) e vai buscar a data ao elemento pai com o XPath ../@data. As horas 18:30 são separadas com Split fields, o T1 passa a 1 com a regex ^T e o requerente é anonimizado.

Resultado: 32 marcações gravadas.

4.5 T4 – Consolidar e publicar

  1. Duplicados: lê a staging, ordena e remove a mesma reserva escrita duas vezes (mesmo clube, campo, data, horas e cliente) para duplicados.csv.
  2. Validação de negócio: faz um Stream lookup a campos + clubes (coberto, iluminação, horário em minutos). O Filter rows compara campos entre si (inicio_min ≥ abertura_min, fim_min ≤ fecho_min) e rejeita campos inexistentes e reservas fora do horário para rejeitadas.csv.
  3. Blocos de 30 minutos: o Calculator calcula o número de blocos (1h30 → 3) e o Clone row cria uma cópia por bloco, numerada. Um pequeno JavaScript calcula a hora do bloco (18:30) e a chave da meteorologia (2026-10-21T18:00).
  4. Meteorologia: faz um Stream lookup a meteo_hora por clube e hora e calcula os alertas: risco_chuva (campo descoberto e probabilidade ≥ LIMITE_CHUVA), precisa_luz (já é noite) e sem_luz (é noite e o campo não tem iluminação).
  5. Conflitos: o Group by conta as reservas por campo, dia e bloco. Mais de uma reserva no mesmo bloco é um conflito, enviado para conflitos.csv.
  6. Saídas: os resultados são escritos em várias saídas em paralelo (cópia das linhas): ocupacao_slot na BD, quadro em JSON e em XML, alertas, conflitos e, com um segundo Group by e um Calculator, a taxa de ocupação por campo e dia (BD e CSV).

5. Jobs

O job j_hacampo.kjb define a ordem e o que acontece quando algo falha:

  1. Preparar base de dados (SQL): cria o esquema e as tabelas se não existirem, insere ou atualiza os clubes e os campos (ON CONFLICT … DO UPDATE) e esvazia a staging. Pode ser corrido várias vezes.
  2. Existem os ficheiros de entrada? Verifica que os 3 ficheiros existem.
  3. Validar XML contra XSD.
  4. T0 – Previsão do tempo. Se falhar (por exemplo, sem internet), escreve um aviso no log e continua com a última previsão guardada. É o único passo que pode falhar sem parar o processo.
  5. T1, T2 e T3 carregam a staging; T4 consolida e publica.
  6. Fim: escreve no log onde estão os resultados e termina com Success. Qualquer falha nos passos 1–3 ou em T1–T4 segue o hop vermelho: regista o erro no log e aborta.

O job tem três parâmetros, passados às transformações: DATA_INICIO e DATA_FIM (semana pedida à API) e LIMITE_CHUVA. Todos os caminhos são relativos (${Internal.Entry.Current.Directory}), por isso a pasta pode ser copiada para outro computador. Pela linha de comandos:

Kitchen.bat -file="...\dataintegration\j_hacampo.kjb" -level=Basic "-logfile=...\data\output\execucao.log"

7. Conclusão e trabalhos futuros

O trabalho mostra um processo ETL completo sobre um problema real: juntar num único quadro as marcações de clubes que usam sistemas diferentes. O processo lê cinco origens (CSV, JSON, XML, PostgreSQL e uma API REST). Limpa e normaliza os dados com expressões regulares, remove repetidos, anonimiza os dados pessoais e aplica regras de negócio: horários, campos existentes, conflitos, luz e chuva. Os resultados ficam na base de dados e em ficheiros JSON, XML e CSV. A separação em transformações de entrada, staging e consolidação torna fácil acrescentar novos clubes.

As principais dificuldades foram as datas e horas escritas de muitas formas diferentes, decidir o que é um erro (que vai para ficheiro) e o que é só um aviso (que continua), e manter a anonimização sem perder a capacidade de detetar duplicados (resolvida com o hash SHA-256).

Trabalhos futuros:

  • Correr o job de hora a hora (agendador do sistema ou Carte) e publicar o JSON automaticamente no site hacampo (FTP/SFTP).
  • Enviar por email ao clube os conflitos e alertas do dia (entrada Mail do job).
  • Receber marcações em tempo real por MQTT/Node-RED em vez de ficheiros.
  • Ligar a clubes reais, com autorização.
